# Database Schema - Firestore Collections

**Project:** Manik Golden Honey Co
**Stage:** 4 - Refine L1 (Detailed Design)
**Date:** 2026-01-24

---

## Overview

Firestore NoSQL database with 10 primary collections. All collections use auto-generated document IDs except where noted.

**Naming conventions:**
- Collections: lowercase, plural (e.g., `products`, `orders`)
- Fields: snake_case (e.g., `created_at`, `reserved_quantity`)
- IDs: auto-generated by Firestore unless specified

---

## Collections

### 1. products

**Purpose:** Product catalog (honey products)

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  name: string,                  // "Wildflower Honey 12oz"
  description: string,           // Product description (markdown)
  price: number,                 // Price in cents (e.g., 1500 = $15.00)
  quantity: number,              // Total physical inventory
  reserved_quantity: number,     // Sum of active reservations
  image_url: string,             // Cloud Storage URL
  active: boolean,               // Visible to customers
  created_at: timestamp,
  updated_at: timestamp
}
```

**Indexes:**
- `active` ASC, `created_at` DESC (list active products)
- `quantity` ASC (low inventory alert)

**Computed fields:**
- `available_quantity = quantity - reserved_quantity` (computed, not stored)

**Constraints:**
- `quantity >= 0`
- `reserved_quantity >= 0`
- `quantity >= reserved_quantity` (admin updates must validate)
- `price > 0`

### 2. customers

**Purpose:** Customer accounts (passwordless auth)

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  email: string,                 // Unique, lowercase
  created_at: timestamp,
  last_login_at: timestamp,
  order_count: number,           // Denormalized for admin dashboard
  total_spent: number            // Denormalized (cents)
}
```

**Indexes:**
- `email` ASC (unique, for login lookup)
- `created_at` DESC (recent customers)

---

### 3. verification_codes

**Purpose:** Email verification codes for passwordless auth

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  email: string,
  code: string,                  // 6-digit code
  attempts: number,              // Failed verification attempts
  expires_at: timestamp,         // 10 minutes from creation
  created_at: timestamp
}
```

**Indexes:**
- `email` ASC, `expires_at` DESC (lookup latest valid code)
- `expires_at` ASC (cleanup old codes)

**TTL:** Auto-delete after 24 hours (Firestore TTL policy on `expires_at`)

### 4. admins

**Purpose:** Admin user accounts

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  email: string,                 // Unique
  password_hash: string,         // bcrypt hash
```

**Indexes:**
- `email` ASC (unique, for login)

**Note:** For MVP, single admin only. Multi-admin support deferred.

### 5. orders

**Purpose:** Customer orders (created after successful payment)

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  customer_id: string,           // FK to customers
  line_items: array<{            // Denormalized order items
    product_id: string,
    product_name: string,        // Snapshot at order time
    quantity: number,
    price_per_unit: number,      // Snapshot (cents)
    total: number                // quantity * price_per_unit
  }>,
  subtotal: number,              // Sum of line_items totals (cents)
  discount_code: string | null,  // Code used (if any)
  discount_amount: number,       // Discount applied (cents)
  total: number,                 // subtotal - discount_amount

  shipping_address: {
    name: string,
    street: string,
    city: string,
    state: string,
    zip: string,
    country: string
  },

  status: string,                // pending, processing, shipped, delivered, cancelled
  cancellation_status: string,   // none, requested, approved, denied

  stripe_payment_intent_id: string,
  stripe_charge_id: string | null,

  created_at: timestamp,
  updated_at: timestamp,
  shipped_at: timestamp | null,
  delivered_at: timestamp | null
}
```

**Indexes:**
- `customer_id` ASC, `created_at` DESC (customer order history)
- `status` ASC, `created_at` DESC (admin filter by status)
- `created_at` DESC (recent orders)
- `cancellation_status` ASC (admin cancellation queue)

**Status values:**
- `pending` - Order created, payment confirmed
- `processing` - Admin preparing shipment
- `shipped` - Order shipped to customer
- `delivered` - Order delivered (terminal state)
- `cancelled` - Order cancelled (terminal state)

### 6. reviews

**Purpose:** Product reviews from verified purchasers

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  product_id: string,            // FK to products
  customer_id: string,           // FK to customers
  order_id: string,              // FK to orders (proof of purchase)

  rating: number,                // 1-5 stars
  review_text: string,           // 10-500 characters

  status: string,                // pending, approved, rejected
  rejection_reason: string | null,

  edit_count: number,            // Track edits (limit to 3)

  created_at: timestamp,
  updated_at: timestamp,
  moderated_at: timestamp | null,
  moderated_by: string | null    // admin_id
}
```

**Indexes:**
- `product_id` ASC, `status` ASC, `created_at` DESC (approved reviews for product)
- `customer_id` ASC, `product_id` ASC (one review per customer per product)
- `status` ASC, `created_at` DESC (admin moderation queue)

**Constraints:**
- One review per `(customer_id, product_id)` combination
- `rating` between 1-5
- `review_text` length 10-500 chars
- `edit_count` <= 3

### 7. inventory_reservations

**Purpose:** Temporary inventory locks during checkout

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  product_id: string,            // FK to products
  quantity: number,              // Reserved quantity
  session_id: string,            // Customer session identifier

  reserved_at: timestamp,
  expires_at: timestamp,         // reserved_at + 15 minutes

  created_at: timestamp
}
```

**Indexes:**
- `product_id` ASC (lookup reservations per product)
- `expires_at` ASC (background job cleanup query)
- `session_id` ASC (customer reservation lookup)

**TTL:** Background job deletes expired (not Firestore TTL, need inventory update)

### 8. promo_codes

**Purpose:** Discount promotional codes

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  code: string,                  // Unique, uppercase (e.g., "LAUNCH10")

  discount_percentage: number,   // 0-100 (e.g., 10 = 10% off)

  min_order_value: number | null,// Minimum order cents (null = no minimum)
  expiration_date: timestamp | null,
  max_redemptions: number | null,// null = unlimited
  one_time_per_customer: boolean,

  used_count: number,            // Denormalized redemption count
  active: boolean,               // Can be used

  created_at: timestamp,
  created_by: string,            // admin_id
  deactivated_at: timestamp | null
}
```

**Indexes:**
- `code` ASC (unique, lookup by code)
- `active` ASC, `created_at` DESC (admin active codes list)

**Constraints:**
- `code` unique
- `discount_percentage` 0-100
- `used_count <= max_redemptions` (if max_redemptions not null)

### 9. promo_code_usage

**Purpose:** Track code redemptions per customer (enforce one-time-per-customer)

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  promo_code_id: string,         // FK to promo_codes
  code: string,                  // Denormalized for convenience
  customer_id: string,           // FK to customers
  order_id: string,              // FK to orders

  discount_amount: number,       // Cents saved
  used_at: timestamp
}
```

**Indexes:**
- `promo_code_id` ASC, `customer_id` ASC (check if customer used code)
- `customer_id` ASC, `used_at` DESC (customer redemption history)
- `promo_code_id` ASC, `used_at` DESC (code usage timeline)

---

### 10. cancellation_requests

**Purpose:** Customer order cancellation requests (admin approval workflow)

**Schema:**
```typescript
{
  id: string,                    // Auto-generated
  order_id: string,              // FK to orders
  customer_id: string,           // FK to customers

  reason: string | null,         // Customer explanation (optional)
  status: string,                // pending, approved, denied

  requested_at: timestamp,
  reviewed_at: timestamp | null,
  reviewed_by: string | null,    // admin_id
  admin_notes: string | null,    // Internal admin notes
  denial_reason: string | null   // Sent to customer if denied
}
```

**Indexes:**
- `order_id` ASC (lookup cancellation for order)
- `status` ASC, `requested_at` DESC (admin pending queue)
- `customer_id` ASC, `requested_at` DESC (customer history)

**Constraints:**
- One cancellation request per order
- Status: `pending` | `approved` | `denied`

## Data Size Estimates (MVP - First Year)

**Assuming:**
- 500 customers
- 2,000 orders total
- 20 products
- 600 reviews (30% review rate)
- 10 promo codes
- 50 cancellation requests (2.5% rate)

**Storage:**
```
products:                 20 docs × 1KB = 20KB
customers:               500 docs × 0.5KB = 250KB
orders:                2,000 docs × 3KB = 6MB
reviews:                 600 docs × 1KB = 600KB
promo_codes:              10 docs × 0.5KB = 5KB
promo_code_usage:      1,200 docs × 0.3KB = 360KB
cancellation_requests:    50 docs × 1KB = 50KB
inventory_reservations:  ~10 docs × 0.5KB = 5KB (active at any time)
verification_codes:      ~50 docs × 0.3KB = 15KB (active at any time)
admins:                    1 doc × 0.5KB = 0.5KB

Total: ~7.3MB
```

**Firestore Costs:**
- Free tier: 1GB storage, 50K reads/day, 20K writes/day
- MVP well within free tier

## Denormalization Strategy

**Where we denormalize:**
1. **Orders:** `line_items` include product name/price snapshot (product may change/delete)
2. **Customers:** `order_count`, `total_spent` (avoid aggregation queries)
3. **Promo codes:** `used_count` (avoid counting usage collection)
4. **Promo code usage:** `code` field (convenience for queries)

**Why:**
- Firestore doesn't support joins
- Snapshot data at order time (historical accuracy)
- Aggregations are expensive (count queries)

**Trade-off:** Write complexity (update multiple documents) vs read simplicity
