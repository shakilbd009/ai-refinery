# Folder Structure Conventions

## General Principles

1. **Flat when possible**: Avoid deep nesting. 2-3 levels is ideal.
2. **Group by feature, not type**: `/features/auth` beats `/controllers/auth-controller.js` + `/services/auth-service.js` scattered across folders
3. **Clear names**: Folder names should be immediately understandable
4. **Consistent**: Use the same pattern across the project

## Standard Structure by Project Type

### Web Application (Frontend + Backend)

```
project-name/
├── client/                # Frontend code
│   ├── src/
│   │   ├── components/    # Reusable UI components
│   │   ├── pages/         # Page-level components (routes)
│   │   ├── hooks/         # Custom React hooks
│   │   ├── utils/         # Helper functions
│   │   ├── styles/        # Global styles
│   │   └── api/           # API client code
│   ├── public/            # Static assets
│   └── tests/             # Frontend tests
├── server/                # Backend code
│   ├── src/
│   │   ├── routes/        # API endpoints
│   │   ├── services/      # Business logic
│   │   ├── models/        # Data models
│   │   ├── middleware/    # Express middleware
│   │   └── utils/         # Helper functions
│   └── tests/             # Backend tests
├── docs/                  # Documentation
├── scripts/               # Build/deploy scripts
└── README.md
```

### Library/Package

```
package-name/
├── src/                   # Source code
│   ├── index.ts           # Main entry point
│   ├── core/              # Core functionality
│   └── utils/             # Helpers
├── tests/                 # Test files (mirror src structure)
├── docs/                  # Documentation
│   ├── api.md             # API reference
│   └── guides/            # Usage guides
├── examples/              # Example usage
├── dist/                  # Build output (gitignored)
├── package.json
├── tsconfig.json
└── README.md
```

### CLI Tool

```
cli-tool/
├── src/
│   ├── commands/          # CLI commands
│   ├── utils/             # Helpers
│   └── index.ts           # Entry point
├── tests/
├── bin/                   # Executable scripts
├── docs/
└── README.md
```

### Microservices

```
project-name/
├── services/
│   ├── auth-service/      # Each service is independent
│   │   ├── src/
│   │   ├── tests/
│   │   ├── Dockerfile
│   │   └── package.json
│   ├── user-service/
│   └── notification-service/
├── shared/                # Shared code/types
├── docs/                  # Overall architecture docs
├── docker-compose.yml
└── README.md
```

## Common Folders Explained

### `/src` vs Root Files
- **Use `/src`** for anything compiled/transpiled (TypeScript, bundled JS)
- **Root level** for config files, docs, scripts that don't get built

### `/tests` vs `__tests__`
- **`/tests`** at root: Separate test directory
- **`__tests__`** co-located: Test files next to source files
- Pick one and be consistent

### `/docs`
- Architecture documentation
- API references
- Guides and tutorials
- NOT for inline code comments

### `/scripts`
- Build scripts
- Deployment automation
- Database seeds/migrations
- Development utilities

### `/public` or `/static`
- Assets served directly (images, fonts, etc.)
- HTML templates
- Files that don't get processed

### `/dist` or `/build`
- Compiled/built output
- Always gitignore this
- Generated by build tools

### `/config`
- Environment-specific configs
- Webpack, Babel, ESLint configs
- Keep config files at root if there are only a few

## Feature-Based Organization

For larger apps, organize by feature instead of technical layer:

```
src/
├── features/
│   ├── auth/
│   │   ├── auth.service.ts
│   │   ├── auth.controller.ts
│   │   ├── auth.model.ts
│   │   └── auth.test.ts
│   ├── tasks/
│   │   ├── tasks.service.ts
│   │   ├── tasks.controller.ts
│   │   ├── tasks.model.ts
│   │   └── tasks.test.ts
│   └── users/
├── shared/                # Shared across features
└── index.ts
```

**Benefits**:
- Related code stays together
- Easy to find everything for a feature
- Easier to extract into separate service later

## What NOT to Do

### ❌ Too Deep
```
src/app/modules/features/user/services/implementations/UserServiceImpl.ts
```
This is 7 levels deep. Refactor to max 3 levels.

### ❌ Ambiguous Names
```
/stuff
/things
/misc
/temp
```
These folders accumulate junk. Use specific names.

### ❌ Mixing Concerns
```
/src
  /api-and-utils-and-helpers
```
Don't combine unrelated things. Split them.

### ❌ Duplicate Information
```
/src/components/UserComponent.tsx
```
Either `/components/User.tsx` OR `/user/UserComponent.tsx`, not both folder and file saying "component"

## Tips

1. **Start simple**: Don't create folders "for future use". Add them when needed.
2. **Consistency matters**: Pick a pattern and stick with it across your entire project
3. **Mirror tests**: Test structure should mirror source structure
4. **Document deviations**: If you diverge from standard patterns, explain why in README or architecture docs
5. **Refactor when it hurts**: If you're getting lost in your own folders, simplify

## Language-Specific Notes

### JavaScript/TypeScript
- Use `/src` for source, `/dist` for build output
- `/node_modules` is always gitignored
- Config files at root (package.json, tsconfig.json, etc.)

### Python
- Use `/src/<package_name>` or flat structure with package at root
- `/tests` mirror `/src` structure
- `__pycache__` and `*.pyc` gitignored

### Go
- Follow Go conventions: `/cmd`, `/pkg`, `/internal`
- One module per repo typically

### Rust
- Use Cargo's conventions: `/src`, `/tests`, `/benches`
- `/target` gitignored

## Validation

Good folder structure should:
- [ ] Make it easy to find related code
- [ ] Be obvious to new developers
- [ ] Not require extensive documentation
- [ ] Scale as the project grows
- [ ] Follow community conventions for the language/framework
